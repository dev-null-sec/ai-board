# 存储后端评估

## 结论

当前版本继续使用 `.ai-board/board.json` 作为默认唯一真相源，不切 SQLite。

下一步如果要增强可追溯性，优先做可选事件日志：`.ai-board/events.jsonl`。它记录每次任务状态变化，但不替代 `board.json`。`board.json` 仍然是当前状态快照，Markdown 仍然从快照生成。

SQLite 暂缓。等项目出现大量任务、复杂查询、跨项目统计、长期并发写入或需要更强事务保证时，再作为可选后端设计。

## 为什么不现在切 SQLite

- 当前数据量很小，任务通常几十条以内，JSON 读取和渲染足够快。
- JSON 对 Git 友好，人和 AI 都能直接审查、修复、合并。
- 现在 CLI 的核心价值是“轻、容易安装、容易理解”，SQLite 会增加迁移、备份、调试和文档复杂度。
- Python 标准库自带 `sqlite3`，但引入数据库后仍然要设计 schema、迁移、导入导出和错误恢复，这些成本暂时不值得。

## 为什么事件日志更适合作为下一步

- 事件日志能补上现在缺的审计能力：谁在什么时候把任务从 inbox 改到 active、scope 怎么变、验收怎么写。
- JSONL 可以一行一个事件，仍然容易被 Git diff、AI 阅读和人工修复。
- 它可以作为旁路增强，不破坏现有 `board.json` 快照模型。
- 后续如果真的要迁到 SQLite，事件日志也能作为导入来源或恢复来源。

## 推荐设计

保留当前文件：

```text
.ai-board/board.json
```

新增可选文件：

```text
.ai-board/events.jsonl
```

每次状态修改追加一条事件，建议字段：

```json
{"ts":"2026-05-14T00:00:00+00:00","actor":"codex","action":"task.started","task_id":"T-0001","before_status":"scheduled","after_status":"active","scope":["src"]}
```

事件日志只做追踪，不作为默认读取源。正常命令仍然读取 `board.json`，避免每次启动都重放事件。

## 什么时候再考虑 SQLite

满足下面任意两类情况，再重新评估 SQLite：

- 单个项目任务超过数百条，JSON diff 和渲染明显变慢。
- 需要按 agent、时间、scope、lane 做复杂筛选和统计。
- 需要跨多个项目聚合看板。
- 多 agent 高频并发写入，当前 lock 文件模型成为瓶颈。
- 需要更正式的审计、恢复、压缩和迁移能力。

## 后续可排任务

- 增加可选 `events.jsonl` 事件日志，先覆盖 `add/schedule/start/complete/archive/block/renew/unlock/goal`。
- 增加 `ai-board history [TASK_ID]`，从事件日志读取任务变更历史。
- 增加 `ai-board doctor`，检查 `board.json` 和事件日志是否基本一致。
- 暂不做 SQLite 后端，直到上面的触发条件出现。
