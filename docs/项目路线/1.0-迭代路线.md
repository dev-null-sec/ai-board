# ai-board 1.0 迭代路线

## 1.0 定义

`ai-board` 1.0 不做“大而全的多 agent 平台”。

1.0 的目标是成为：

> 一个本地优先、git 联动、可验证、可审计的 AI 项目治理 CLI。

这意味着 `ai-board` 的核心价值不是让更多 agent 同时干活，而是让 AI 对项目做出的每一次改动都能被归属、验证、审计和回滚。

## 路线原则

- 本地优先：默认继续使用本地文件和 git，不引入云服务。
- git 联动：把 git 当成回滚底座和提交关口，而不是替代 git。
- 可验证：验收不能长期只依赖自由文本。
- 可审计：人能快速看懂最近 AI 做了什么、改了什么、验了什么。
- 多 agent 可选：默认关闭，多 agent 只做路径级防撞和协作提示，不承诺分布式协作平台。
- 文档和 skill 瘦身：让 AI 自然执行流程，不靠塞长提示词硬背规则。

## 1.0 最低能力

### scope gate

能在 git commit 前发现并阻止越界改动。

最低要求：

- 支持 `scope_gate=off/suggest/required`。
- 能检查 staged diff 是否落在 active task scope 内。
- 能通过 pre-commit hook 接入提交关口。
- 能在 CI 或本地命令中复用同一套检查。

### verification evidence

验收不只靠 `complete --verification "测试通过"` 这种自由文本。

最低要求：

- 新增 `verify` 或等价机制。
- 工具能运行验证命令，保存命令、退出码、时间和输出摘要。
- `complete` 可以引用验证记录。
- 手工验收仍允许，但要明确标记为 manual。

### review

人能快速看懂最近 AI 做了什么。

最低要求：

- 提供 `review --since` / `review --from` 或等价入口。
- 汇总任务状态变化、改动文件、scope 是否匹配、验证证据和遗留问题。
- 面向人输出，不只是 dump JSON。

### schema migration

board 数据可以安全升级。

最低要求：

- 文档化 schema。
- 提供迁移路径和 dry-run。
- 迁移前自动备份。
- 测试覆盖旧 schema 到新 schema。

### onboard 继续强化

新项目不猜方向，已有项目先识别状态。

最低要求：

- 空项目继续要求方向确认。
- 轻量项目把文件名、目录名当假设，不当事实。
- 已有项目优先识别 git、现有文档、未提交变更和项目边界。

### multi-agent 保持可选

默认关闭，开启后做路径级防撞。

最低要求：

- 不把 1.0 定义成跨机器锁或实时协作平台。
- 不承诺语义级冲突检测。
- 多 agent 能力继续服务“避免同时碰同一批文件”，不拖累单 agent 默认体验。

### README 和 skill 继续瘦身

让用户用短提示词指挥 AI，让 AI 从项目文件和 CLI guide 读取规则。

最低要求：

- README 面向人，说明项目是什么、为什么用、怎么交给 AI。
- `skills/ai-board/SKILL.md` 只做发现入口。
- 复杂流程放在 `ai-board skills get core --full`，默认 guide 保持短。

## 版本阶梯

### 0.2：git scope gate MVP

目标：把 scope 约束从 `doctor` 事后发现推进到 git 提交关口。

范围：

- hook install/status/uninstall。
- staged diff scope 检查。
- `scope_gate=suggest|required`。
- required 模式下可阻断 commit。
- README / CLI guide 用克制口径说明：这是提交关口，不是运行时文件拦截。

对应当前任务：

- `T-0110`：设计 0.2 git scope gate 规格。
- `T-0111`：实现 staged diff 与 task scope gate 核心检查。
- `T-0112`：实现 git hook 安装与 scope gate 命令。
- `T-0113`：补齐 0.2 scope gate 文档、AI 指南与回归验收。

### 0.3：verification evidence

目标：让验收从“agent 自述”升级为“工具记录证据”。

范围：

- 评估并实现 `verify`。
- 保存验证命令、退出码、时间和输出摘要。
- `complete` 可引用验证记录。
- 区分 automated verification 和 manual verification。

当前已有需求：

- `T-0114`：评估 0.3 verification evidence 方案。

### 0.4：human review

目标：让人能快速审计最近 AI 做了什么。

范围：

- `review --since` / `review --from`。
- 汇总任务、事件、改动文件、scope 匹配、验证证据、leftovers。
- 输出给人看的摘要，不要求 Web UI。

### 0.5：schema migration

目标：让长期项目敢托付 `.ai-board/board.json`。

范围：

- schema 文档。
- 迁移命令和 dry-run。
- 迁移前备份。
- 旧 schema 回归测试。

### 0.6：多 agent 可选能力打磨

目标：保持多 agent 可选，不扩成完整平台。

范围：

- 继续强化路径级防撞和 notice 收口。
- 评估 current agent 机制。
- 不承诺跨机器锁、实时通信或语义级冲突检测。

### 1.0：稳定闭环

目标：稳定 CLI、稳定 schema、稳定 git gate、稳定验收证据、稳定 review 闭环。

1.0 发布前必须确认：

- scope gate 已稳定。
- verification evidence 已稳定。
- review 已能支撑人类审计。
- schema migration 已可用。
- onboarding 仍不猜项目方向。
- multi-agent 默认关闭且边界清楚。
- README、skill、CLI guide 口径一致。

## 暂不做

- Web UI。
- 云同步。
- 分布式锁。
- 语义级代码冲突检测。
- 运行时文件写入拦截。
- 把 Markdown 当数据库。
- 为了“看起来成熟”引入重依赖。

## 流程教训

重要方向不能只写在聊天里，也不能只写成一句 current goal。

后续凡是用户确认了版本路线、1.0 定义、能力边界或长期取舍，都必须至少落到：

- `docs/决策记录.md`；
- 一份 `docs/项目路线/` 下的路线或评估文档；
- `.ai-board/board.json` 的需求池或下一批任务。

否则下一次 agent 接手时仍然会被迫从聊天或文件名猜方向，这违反 ai-board 自己的设计原则。
