# 0.4 human review 方案

## 背景

0.2 把 scope 约束推进到 git 提交关口。0.3 把验收从自由文本推进到 verification evidence。

下一步是 0.4：让人能快速看懂最近 AI 做了什么。

现在已经有 `history`、`show`、`doctor`、`gate pre-commit`、git diff 和 generated board，但它们各自回答的是局部问题：

- `history` 展示事件流水；
- `show` 展示单个任务详情；
- `doctor` 检查结构健康；
- git diff 展示代码实际变化；
- 生成看板展示当前队列和归档。

人真正需要的是一份面向审计的摘要：

> 最近这段时间，哪些任务动过，谁动的，改了哪些文件，scope 有没有越界，验收证据是什么，还有什么遗留或验证债务。

0.4 的 `review` 就做这件事。

## 目标

`review` 不是项目管理看板，也不是 Web UI。

它的目标是把已经存在的事实源整理成人能扫读的审计报告：

- 任务：最近新增、启动、完成、归档、阻塞、重开了哪些任务；
- agent：这些动作由谁触发；
- 文件：最近 git diff 里实际改了哪些路径；
- scope：这些路径是否落在任务声明的 scope 里；
- 验证：任务引用了哪些 verification evidence，证据类型和状态是什么；
- 遗留：leftovers、deferred_verification、verification debt 是否还没收口；
- 风险：未提交变更、越界改动、手写验收、force 完成、过宽 scope、生成看板过期等。

它回答的是：

> 我作为人类 reviewer，今天要不要放心继续往下走？

## 非目标

0.4 不做：

- Web UI；
- 复杂报表系统；
- token 计费器；
- 语义级代码审计；
- 自动判断业务正确性；
- 自动生成 PR review；
- 替代 git diff；
- 替代测试、CI 或安全扫描；
- 长期指标数据库。

0.4 只做本地、轻量、文本输出。

## 命令入口

建议新增：

```bash
ai-board review
ai-board review --since 2026-06-09
ai-board review --from T-0129
ai-board review --agent codex
ai-board review --format json
```

默认行为：

- 如果没有参数，回顾最近一段事件，建议默认 24 小时或最近 20 条任务相关事件；
- `--since` 按时间过滤事件；
- `--from TASK_ID` 从某个任务首次出现的事件之后开始；
- `--agent` 只看某个 agent 的动作；
- 默认输出人类可读文本；
- `--format json` 输出结构化摘要，供后续工具或测试使用。

参数设计要克制。0.4 先不要引入复杂查询语言。

## 输出结构

人类可读输出建议包含这些段落。

### 1. Review Window

说明本次 review 范围：

- 时间窗口；
- 事件数量；
- 涉及任务数量；
- 涉及 agent；
- 当前 git 状态是否干净。

示例：

```text
review window: since 2026-06-09T00:00:00+08:00
events: 42
tasks: T-0129, T-0135
agents: codex
git: dirty (6 tracked files changed, 3 untracked)
```

### 2. Task Changes

按任务汇总最近变化：

```text
T-0135 实现 complete --verification-id 与验证证据展示
status: archived
agent: codex
scope: src/ai_board/cli.py, src/ai_board/operations.py, tests/test_cli.py
events: start -> verification.recorded x3 -> complete -> archive
leftovers: 无
```

这里不要 dump 全部事件。完整流水仍交给 `history`。

### 3. File Changes

从 git 获取实际变更路径，最小可先使用：

- `git status --short --untracked-files=all`
- `git diff --name-only`
- 可选：`git diff --cached --name-status`

review 应展示：

- tracked changed；
- staged changed；
- untracked；
- board 系统副作用；
- 业务文件改动。

如果文件可以归属到 active/done/archived 任务 scope，应显示归属；归属不到则标为 unclaimed。

### 4. Scope Check

review 不替代 `gate pre-commit`，但应该复用同一套路径判断规则，回答：

- 文件是否落在任务 scope 内；
- 是否只有 ai-board 系统副作用；
- 是否存在宽 scope；
- 是否存在多个任务都可能覆盖同一文件；
- 是否存在未归属的业务变更。

输出示例：

```text
scope check:
- ok: src/ai_board/cli.py covered by T-0135
- ok: tests/test_cli.py covered by T-0135
- system: .ai-board/board.json
- risk: README.md changed but no reviewed task scope covers it
```

0.4 可以先只做 warning，不阻断。

### 5. Verification Summary

消费 0.3 evidence：

- 每个 done/archived 任务引用了哪些 verification ID；
- evidence 是 automated、manual、uat、deferred 还是 blocked；
- 是否存在 failed evidence；
- 是否存在 `verification_force=true`；
- 是否存在 deferred_verification 或未关闭 verification debt；
- 是否只有自由文本 `verification`，没有 evidence。

输出示例：

```text
verification:
- T-0135: V-0003 automated/passed, V-0004 automated/passed
- T-0129: V-0006 automated/passed, V-0007 automated/passed
- risk: T-0008 completed with manual text only
- debt: T-0010 deferred full integration test
```

### 6. Review Risks

最后给一段风险摘要，越短越好。

风险分级建议：

| 等级 | 含义 |
| --- | --- |
| `issue` | 明显结构错误，应该先修 |
| `risk` | 不一定错误，但人应该看一眼 |
| `note` | 普通提示 |

常见风险：

- generated docs stale；
- active task 无 scope；
- done/archived 任务引用缺失 evidence；
- 任务只有自由文本 verification；
- verification_force 没有 leftovers；
- deferred/blocked verification debt 未关闭；
- git 有未归属业务改动；
- scope gate required 但 hook 缺失；
- 当前状态指向已归档任务；
- 看板为空但路线文档仍有未完成阶段。

## 与现有命令的分工

| 命令 | 做什么 | 不做什么 |
| --- | --- | --- |
| `history` | 展示事件流水 | 不汇总 git diff、scope、验证强度 |
| `show` | 展示单个任务详情 | 不回答最近整体发生了什么 |
| `doctor` | 检查结构健康 | 不做审计摘要，不解释最近改动 |
| `gate pre-commit` | 在提交关口检查 staged diff | 不汇总任务历史和验证证据 |
| `status` | 给队列数量 | 不展开风险 |
| `next` | 给下一步动作建议 | 不做回顾 |
| `review` | 汇总最近 AI 行为，给人审计 | 不替代 diff、测试、CI、人工 code review |

一句话：

- `doctor` 是体检；
- `history` 是流水；
- `gate` 是关口；
- `review` 是给人看的复盘。

## 数据来源

0.4 应尽量复用已有事实源：

| 数据 | 来源 |
| --- | --- |
| 任务状态和 scope | `.ai-board/board.json` |
| verification evidence | `.ai-board/board.json` |
| 操作流水 | `.ai-board/events.jsonl` |
| notice 状态 | `.ai-board/messages.jsonl` |
| 实际文件变更 | git status / diff |
| scope 覆盖判断 | `src/ai_board/gate.py` / 现有 scope 判断 |
| generated docs stale | render 对比逻辑，参考 doctor |

原则：

- review 只汇总，不创造新事实；
- 发现结构问题时提示用户跑 `doctor` 或对应修复命令；
- 不偷偷修改 board；
- 不自动 stage、commit 或清理文件。

## 0.4 最小实现范围

建议 0.4 MVP 分三步。

### T-0.4-1：review 数据聚合

实现内部聚合函数：

- 读取 board；
- 读取 events；
- 按 `--since` / `--from` / `--agent` 过滤；
- 找出相关任务；
- 汇总任务生命周期、owner、scope、verification、leftovers；
- 输出 JSON 结构，方便测试。

### T-0.4-2：git diff 和 scope 归属

加入 git 视角：

- 读取 tracked / staged / untracked 文件；
- 区分 ai-board 系统副作用和业务文件；
- 判断业务文件是否被相关任务 scope 覆盖；
- 标出 unclaimed changes。

0.4 先 warning，不阻断。

### T-0.4-3：人类可读输出

实现默认文本输出：

- review window；
- task changes；
- file changes；
- verification summary；
- risks。

再补 `--format json`，或先以 JSON 为测试基准、文本为人用展示。

## 测试矩阵

最低测试：

| 场景 | 期望 |
| --- | --- |
| 无事件 | `review` 输出 no recent activity |
| 最近完成一个任务 | 展示任务、事件链、verification、leftovers |
| `--since` 过滤 | 只展示窗口内事件 |
| `--from T-0001` | 从指定任务首次事件后汇总 |
| `--agent codex` | 只展示该 agent 触发的事件和相关任务 |
| 任务引用 automated evidence | verification summary 标为 automated/passed |
| 任务只有自由文本 verification | 标为 risk |
| 存在 deferred_verification | 标为 debt/risk |
| git 有 scope 内业务改动 | file changes 标为 covered |
| git 有 scope 外业务改动 | file changes 标为 unclaimed risk |
| 只有 `.ai-board` 和生成看板变更 | 标为 system side effects |
| 非 git 项目 | review 仍可输出任务和事件，git 部分提示 unavailable |
| events 损坏 | 返回可读错误，建议修复事件日志 |
| `--format json` | 输出稳定字段，便于回归测试 |

## 输出字段建议

JSON 输出建议先保持浅结构：

```json
{
  "window": {
    "since": "",
    "from_task": "",
    "agent": ""
  },
  "tasks": [
    {
      "id": "T-0135",
      "title": "实现 complete --verification-id 与验证证据展示",
      "status": "archived",
      "owner_agent": "codex",
      "scope": [],
      "events": ["task.start", "verification.recorded", "task.complete", "task.archive"],
      "verification_ids": ["V-0003", "V-0004"],
      "leftovers": "无",
      "risks": []
    }
  ],
  "files": [
    {
      "path": "src/ai_board/cli.py",
      "state": "modified",
      "kind": "business",
      "covered_by": ["T-0135"],
      "risks": []
    }
  ],
  "risks": [
    {
      "level": "risk",
      "message": "README.md changed but no task scope covers it"
    }
  ]
}
```

不要在 0.4 初版里追求完整审计数据库。字段稳定比字段多更重要。

## 与后续版本的关系

0.4 是 human review 的基础层。

后续可以接：

- 0.5 schema migration：review JSON 输出字段也应纳入兼容考虑；
- 0.6 multi-agent：review 可按 agent 汇总 notice、锁、scope 冲突和未收口消息；
- 1.0 release gate：发布前可以跑 `doctor`、`conflicts`、`review --since <last tag>` 作为人工检查清单；
- usage/context observability：可以从 review 风险中提炼长期指标，但不要在 0.4 先做指标平台。

## 结论

0.4 应实现 `review`。

它的价值不是生成漂亮报告，而是让人少翻三处东西：

- 不用单独读事件流水才能知道最近发生了什么；
- 不用手动对照 task scope 和 git diff 才知道有没有越界；
- 不用翻每个 task 才知道验收证据和遗留问题。

但边界也要清楚：`review` 只能整理事实，不能替人判断代码是否真的正确。

这符合 ai-board 的 1.0 定义：本地优先、git 联动、可验证、可审计的 AI 项目治理 CLI。
