# 0.3 verification evidence 方案

## 背景

ai-board 目前的完成流程主要依赖：

```bash
ai-board complete T-0001 --verification "tests passed"
```

这能提醒 agent 写验收结果，但它本质上仍是自由文本。工具无法知道：

- 命令是否真的运行过；
- 退出码是什么；
- 输出里是否有失败；
- 验证发生在任务开始前还是完成后；
- 验证是否覆盖了任务声明的范围；
- 哪些验证只是人工确认；
- 哪些验证其实被延期了。

0.2 已经把 scope 约束推进到 git 提交关口。0.3 应该把验收从“agent 自述”推进到“工具记录证据”。

## 目标

0.3 的目标是：

> 让任务完成时能引用真实、可审计的验证证据，而不是只靠一句自由文本。

最低能力：

- 新增 `verify` 或等价命令；
- 工具能记录验证命令、退出码、时间、输出摘要；
- `complete` 可以引用验证记录；
- 手工验证仍允许，但必须明确标记为 manual；
- 无法全量验证时，不伪装成通过，而是记录 deferred / blocked verification。

## 非目标

0.3 不做：

- 复杂测试平台；
- CI 替代品；
- 测试覆盖率分析；
- 自动判断业务是否正确；
- 长日志全文数据库；
- Web UI；
- 云端证据存储；
- agent runtime 或自动执行器。

## 证据类型

参考 GSD Core 的 verify-work / UAT / verification debt 思路，ai-board 0.3 建议支持五类证据。

| 类型 | 含义 | 能否单独支撑 complete |
| --- | --- | --- |
| `automated` | 工具实际运行命令，记录退出码和输出摘要 | 可以，前提是退出码为 0 |
| `manual` | 人或 agent 说明手工检查结果 | 可以，但审计强度较低，需显式标记 |
| `uat` | 用户逐项确认功能是否符合预期 | 可以，适合 UI/体验/需求确认 |
| `deferred` | 本轮无法全量验证，记录原因和后续条件 | 不应单独支撑无遗留 complete |
| `blocked` | 验证被外部条件阻塞 | 不应 complete，应 block 或留下明确 leftovers |

关键原则：

- `deferred` 不是“通过”，是债务；
- `blocked` 不是“通过”，是阻塞；
- `manual` 可以存在，但不能伪装成 automated；
- `complete` 可以允许带 deferred，但必须进入 leftovers 或 deferred_verification；
- `review` 和 `next` 后续必须能优先暴露未关闭验证债务。

## 证据可信度分层

0.3 之后，`verification` 不再只有“写了一句话”的含义。不同证据的可信度和适用场景应明确展示，避免 AI 把弱证据包装成强证据。

| 类型 | 状态 | 可信度 | 适用场景 | 展示口径 |
| --- | --- | --- | --- | --- |
| `automated` | `passed` / `failed` | 高 | 单元测试、lint、构建、CLI smoke test | 工具实际运行命令，有退出码和输出摘要 |
| `manual` | `passed` / `failed` / `skipped` | 中 | 无法自动化但 agent 或人手工检查过 | 明确标为 manual，不得暗示为自动测试 |
| `uat` | `passed` / `failed` / `skipped` / `blocked` | 高，但依赖人工输入 | UI、体验、需求符合度、用户确认 | 明确是用户验收项，展示 item 和备注 |
| `deferred` | `deferred` | 不是通过 | 环境、账号、共享验证资源或时间窗口导致本轮无法全量验证 | 作为 verification debt 展示 |
| `blocked` | `blocked` | 不是通过 | 验证被外部条件阻塞，继续完成会误导 | 应推动任务 block，或在 leftovers 中显式保留风险 |

原则：

- 自动证据回答“命令有没有真实跑过”。
- UAT 证据回答“用户认为它是不是符合预期”。
- manual 证据只是补充说明，不应伪装成自动或用户确认。
- deferred / blocked 是债务和阻塞，不是通过。
- `show`、`review` 和归档视图应尽量保留证据类型，不只展示一句 summary。

## 建议数据模型

短期仍保留 `.ai-board/board.json` 作为真相源。

建议新增顶层字段：

```json
{
  "verifications": [
    {
      "id": "V-0001",
      "task_id": "T-0001",
      "kind": "automated",
      "status": "passed",
      "command": "uv run python -m unittest discover -s tests",
      "exit_code": 0,
      "summary": "Ran 121 tests in 2.1s OK",
      "output_excerpt": "Ran 121 tests in 2.1s\n\nOK",
      "created_at": "2026-06-09T12:00:00+08:00",
      "agent": "codex",
      "scope": ["tests", "src/ai_board"],
      "evidence_path": ""
    }
  ]
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `id` | 验证记录 ID，例如 `V-0001` |
| `task_id` | 关联任务 |
| `kind` | `automated` / `manual` / `uat` / `deferred` / `blocked` |
| `status` | `passed` / `failed` / `skipped` / `blocked` / `deferred` |
| `command` | 自动验证命令；非自动验证可为空 |
| `exit_code` | 自动验证退出码；非自动验证可为空或 null |
| `summary` | 短摘要，供 show/review 展示 |
| `output_excerpt` | 截断后的输出片段，不保存无限长日志 |
| `created_at` | 记录时间 |
| `agent` | 执行或记录验证的 agent |
| `scope` | 验证覆盖范围，可来自任务 `verify_scope` 或命令参数 |
| `evidence_path` | 可选外部证据路径，例如报告文件 |

事件日志应追加：

- `verification.recorded`
- `verification.failed`
- `verification.deferred`
- `verification.linked`

## 命令设计

### 自动验证

建议命令：

```bash
ai-board verify T-0001 --agent codex --run "uv run python -m unittest discover -s tests"
```

行为：

- 执行命令；
- 记录开始/结束时间；
- 记录退出码；
- 截断保存 stdout/stderr 摘要；
- 退出码为 0 时 `status=passed`；
- 退出码非 0 时 `status=failed`，命令本身返回非零；
- 写入 `V-xxxx` 验证记录和事件日志；
- 不自动 complete 任务。

注意：

- 命令默认在项目根执行；
- 0.3 暂不实现复杂 shell sandbox；
- Windows / PowerShell quoting 要写进测试和文档；
- 输出截断策略要稳定，例如默认保存前后各若干行或固定字符数。

### 手工验证

建议命令：

```bash
ai-board verify T-0001 --agent codex --manual "手工打开页面确认按钮状态正常"
```

行为：

- 不运行命令；
- `kind=manual`；
- `status=passed` 或用户指定；
- 输出时明确显示 manual，避免伪装成自动测试。

### 用户验收

0.3 可以先不做完整交互式 UAT，但数据模型应预留。

最小命令可以是：

```bash
ai-board verify T-0001 --agent codex --uat "用户确认 JSON 输出格式符合预期"
```

后续再扩展为逐项 UAT：

```bash
ai-board verify T-0001 --uat-item "默认输出仍为 3" --status passed
ai-board verify T-0001 --uat-item "JSON 输出为 compact object" --status passed
```

建议 UAT 最小记录结构：

```json
{
  "id": "V-0003",
  "task_id": "T-0001",
  "kind": "uat",
  "status": "passed",
  "summary": "用户确认 JSON 输出符合预期",
  "items": [
    {
      "text": "默认输出仍为 3",
      "status": "passed",
      "note": ""
    },
    {
      "text": "JSON 输出为 compact object",
      "status": "passed",
      "note": "字段顺序和 README 示例一致"
    }
  ],
  "agent": "codex",
  "created_at": "2026-06-09T12:00:00+08:00"
}
```

UAT 不建议做成复杂表单系统。0.3/0.4 的合理形态是：

- `verify --uat "一句总体验收"`：记录一条简单 UAT 证据。
- 后续可扩展 `--uat-item TEXT --status passed|failed|skipped|blocked --note TEXT`。
- 当 UAT item 失败时，工具不自动修复；它只记录事实，并建议新建修复任务或把当前任务 reopen。
- 用户没有明确确认时，AI 不应自行创建 `uat/passed`，只能记录 `manual` 或 `deferred`。

### 延期验证

建议命令：

```bash
ai-board verify T-0001 --agent codex --deferred "全量集成测试需要等待测试环境释放"
```

行为：

- `kind=deferred`；
- `status=deferred`；
- 不表示通过；
- `next` 和 `review` 后续应优先提醒；
- `complete` 引用 deferred 时必须要求 leftovers 或 deferred_verification。

延期验证应当被当作 verification debt，而不是一种“软通过”。最小字段建议：

| 字段 | 说明 |
| --- | --- |
| `reason` | 为什么本轮不能验证，例如环境不可用、账号失效、共享测试范围被锁 |
| `resume_condition` | 什么时候可以恢复验证，例如测试环境释放、用户提供账号、依赖任务归档 |
| `expected_command` | 后续应运行的命令或检查动作，可为空 |
| `owner` | 谁应负责收口，默认沿用 task owner 或记录 agent |
| `created_at` | 债务产生时间 |
| `closed_at` | 后续验证完成后关闭 |
| `closed_by_verification_id` | 用哪条新证据关闭债务 |

### 阻塞验证

建议命令：

```bash
ai-board verify T-0001 --agent codex --blocked "测试账号不可用"
```

行为：

- `kind=blocked`；
- `status=blocked`；
- 建议任务进入 `blocked`，或 complete 时强提醒。

blocked 与 deferred 的区别：

- `deferred`：任务可以在记录遗留风险后暂时完成，但后续必须收口验证。
- `blocked`：验证条件缺失到足以影响任务真实性，默认不应 complete；更适合 `block`、等待条件、或拆出前置任务。

## verification debt 生命周期

verification debt 是“任务已经推进，但验证还没真正闭环”的显式记录。

生命周期建议：

| 阶段 | 触发 | 工具行为 |
| --- | --- | --- |
| 产生 | `verify --deferred`、`verify --blocked`、或 `complete --force` 引用未通过证据 | 写入 evidence，任务详情和 review 中标记 debt |
| 暴露 | `next`、`show`、`review`、`doctor` | 优先提示未关闭 debt，不让 archived 任务把问题藏起来 |
| 恢复验证 | 后续运行 `verify --run`、`verify --manual` 或 `verify --uat` | 新证据可引用旧 debt，或在任务 reopen 后完成 |
| 关闭 | 新证据通过，或用户明确废弃该验证要求 | debt 记录 `closed_at` 和 `closed_by_verification_id`，review 不再当作未收口 |
| 转化 | debt 变成独立修复需求、外部阻塞或不再适用 | 新建任务、block 原任务，或 archive 并记录决策 |

规则建议：

- archived 任务仍可带未关闭 verification debt；这不是数据错误，但必须被 `review` 暴露。
- `doctor` 不应因为存在 debt 就默认失败；它应检查 debt 是否结构完整、是否过久未收口、是否没有恢复条件。
- 如果 debt 关联的任务已归档很久且没有关闭条件，`review` 应提示人类决定：关闭、转新任务、或承认废弃。
- debt 不应只存在于 `leftovers` 自由文本里，至少应有一条 `deferred` 或 `blocked` evidence。

## complete 关系

### 推荐参数

```bash
ai-board complete T-0001 --verification-id V-0001 --leftovers "无"
```

或：

```bash
ai-board complete T-0001 --verification-id V-0001 --verification-id V-0002
```

保留旧参数：

```bash
ai-board complete T-0001 --verification "tests passed"
```

但旧参数应被视为 manual-style free text，而不是 automated evidence。

### complete 校验规则

建议 0.3 规则：

| 场景 | 行为 |
| --- | --- |
| 引用至少一个 passed automated/manual/uat 证据 | 允许 complete |
| 只引用 deferred | 允许但必须有 leftovers 或 deferred_verification |
| 只引用 blocked | 不建议 complete，提示 block |
| 引用 failed automated | 默认拒绝，除非 `--force` 并写 leftovers |
| 无验证证据但有 `--verification` 文本 | 兼容允许，但提示这是自由文本，建议使用 `verify` |
| 无任何验证信息 | 继续拒绝或保持现有要求 |

更细的规则：

- passed `automated`：可以支撑 complete。
- passed `manual`：可以支撑 complete，但 review 应标出它不是自动证据。
- passed `uat`：可以支撑 complete，适合用户体验和需求确认。
- failed `automated` / `manual` / `uat`：默认拒绝 complete；`--force` 必须写 leftovers 或 deferred_verification。
- skipped `manual` / `uat`：不能单独支撑 complete；必须有其他 passed 证据或明确 leftovers。
- deferred：不能单独支撑“无遗留”的 complete；必须写 deferred_verification 或 leftovers。
- blocked：默认不应 complete，建议 `block`；如果强制 complete，review 必须高亮。

当前已实现的 `complete --verification-id` 是保守 MVP：只允许 `status=passed` 直接完成，非 passed 必须 `--force` 且写风险说明。后续如果实现 `deferred` / `blocked` 命令，应沿用上面的语义，而不是把所有非 failed 都当作可完成。

## 与 verify_scope 的关系

现有 task 支持 `verify_scope`。0.3 应使用它提升验收诚实度。

规则建议：

- 如果 task 有 `verify_scope`，`verify` 默认显示建议验证范围；
- `verify --scope` 可以声明本次验证实际覆盖范围；
- 若 `verify_scope` 被 active lock 阻塞，`next` 已有基础提示，后续可更明确；
- complete 时如果验证证据没有覆盖 `verify_scope`，给 warning，不在 0.3 强拦。

## 与 0.4 review 的关系

0.3 只负责记录证据。0.4 review 应消费这些证据。

review 应回答：

- 哪些任务完成了；
- 每个任务引用了哪些验证证据；
- 哪些证据是 automated，哪些是 manual；
- 是否存在 failed/deferred/blocked 验证；
- 归档任务是否仍有未关闭验证债务；
- 验证命令和任务 scope 是否大致匹配。

`next` 和 `review` 的职责边界建议：

| 命令 | 职责 |
| --- | --- |
| `next` | 给下一步动作建议：先收口 debt、恢复验证、reopen 任务、还是继续排新任务 |
| `show` | 展示单个任务的证据、debt、force 风险和 leftovers |
| `history` | 展示证据产生、任务完成、归档和后续关闭 debt 的事件链 |
| `doctor` | 检查结构问题：悬空证据、跨任务引用、force 无风险说明、debt 缺恢复条件 |
| `review` | 给人类审计摘要：最近完成了什么、证据强度如何、哪些债务未收口 |

`next` 的优先级建议：

1. 存在 active 任务且 owner/scope 正常：继续当前任务。
2. 存在未关闭 verification debt：优先恢复验证或转成新任务。
3. 存在 done 未归档且缺证据：先补验收或 reopen。
4. 看板为空但路线文档有未完成阶段：提示拆下一批任务。
5. 再从 scheduled / inbox 里推荐新任务。

这能避免“任务都归档了，但实际上验收问题还留着”的假完成。

## 对现有路线的影响

0.3 建议拆成两步：

1. 设计并实现最小 `verify` 记录能力；
2. 再扩展 complete 引用和 review/next 消费。

如果需要更稳，可以先做：

- `verify --manual`；
- `verify --run`；
- `complete --verification-id`；
- `show` 展示验证记录；
- `doctor` 检查引用不存在或 failed evidence。

UAT 和 deferred debt 可以在 `T-0129` 中继续细化，不必全部塞进第一版实现。

## 测试矩阵

最低测试：

| 场景 | 期望 |
| --- | --- |
| `verify --run` 命令成功 | 创建 `automated/passed` 记录，退出码 0 |
| `verify --run` 命令失败 | 创建 `automated/failed` 记录，命令返回非零 |
| 输出很长 | 摘要被截断，board 不膨胀 |
| `verify --manual` | 创建 `manual/passed` 记录 |
| `verify --deferred` | 创建 `deferred` 记录，不被当作通过 |
| `complete --verification-id V-0001` | 任务完成并引用证据 |
| 引用不存在的 verification ID | complete 失败 |
| 引用 failed evidence | complete 默认失败或要求 force |
| 旧 `complete --verification` | 兼容通过，但不生成 automated evidence |
| `show T-0001` | 展示关联验证记录摘要 |
| `doctor` | 检查损坏或悬空 verification 引用 |

UAT / debt 扩展测试：

| 场景 | 期望 |
| --- | --- |
| `verify --uat` 简单通过 | 创建 `uat/passed` 记录，show 显示为用户验收 |
| `verify --uat-item` 多条项目 | 保存 item 状态和备注，review 汇总 passed/failed/skipped |
| UAT item failed | complete 默认拒绝，或要求 `--force` 和 leftovers |
| `verify --deferred` | 创建 `deferred` debt，不被当作通过 |
| `verify --blocked` | 创建 `blocked` 证据，并建议 block 任务 |
| complete 引用 passed automated + deferred | 允许但必须留下 deferred_verification |
| complete 只引用 deferred | 拒绝无遗留完成 |
| archived 任务存在未关闭 debt | doctor 不一定失败，review/next 必须提示 |
| 后续 passed evidence 关闭 debt | debt 不再出现在未收口列表 |
| debt 引用不存在的 closing evidence | doctor 报结构问题 |

## 结论

0.3 应实现 verification evidence。

它是 1.0 “可验证”承诺的核心步骤，也是 ai-board 从“记账工具”走向“能验账的治理 CLI”的关键。

实现上要克制：

- 不做测试平台；
- 不做 CI；
- 不做复杂 UAT 系统；
- 先把证据记录、引用和审计链路打通。

建议后续进入实现排期：

1. `verify` 最小数据模型与事件日志；
2. `verify --run` / `verify --manual`；
3. `complete --verification-id`；
4. `show` / `doctor` 展示与检查；
5. 再由 `T-0129` 细化 UAT 和 deferred debt。
