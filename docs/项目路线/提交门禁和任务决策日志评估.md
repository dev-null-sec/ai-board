# 提交门禁和任务决策日志评估

## 结论

当前不默认引入强制提交门禁，也不立即实现完整任务决策日志。

更合适的路线是：

- 把 scope 提交检查作为可选模板或示例脚本提供，而不是默认启用。
- 把任务决策日志先设计成轻量可选能力，优先服务“复杂任务为什么这么做”的记录，不替代 `.ai-board/events.jsonl`。
- 继续保持 ai-board 的默认体验轻量：JSON 是当前状态真相源，事件日志记录状态变化，Markdown 是生成视图。

## 可选提交门禁

pre-commit 或提交前检查可以帮助发现这类问题：

- 当前 active task 的 scope 与本次 git diff 明显不匹配。
- agent 还没 start 任务就改了代码。
- 生成看板过期，忘了运行 `ai-board render`。

但它不适合现在默认开启：

- ai-board 目前定位是轻量本地 CLI，默认强门禁会增加安装和调试成本。
- 用户可能在修急问题、整理文档或合并其他 agent 成果，强制阻断容易制造额外摩擦。
- scope 是协作提醒和防撞边界，不是安全沙箱；用 pre-commit 强行解释所有改动，误报会比较多。

推荐做法：

- 后续提供 `examples/hooks/` 或文档示例，给需要更严格流程的项目自行启用。
- 检查结果默认给 warning；是否阻断提交交给项目自己决定。
- 不把 pre-commit 作为运行时依赖，也不把它写进默认初始化流程。

## 任务决策日志

`ai-board note` 或 `.ai-board/tasks/T-XXXX.md` 可以补充事件日志解决不了的问题：

- 为什么选择这个方案，而不是另一个方案。
- 任务推进中的关键权衡、临时约定和复盘。
- 多 agent 交接时，人类可读的上下文。

它和现有事件日志的分工应该很清楚：

- `.ai-board/events.jsonl` 记录“发生了什么”：add、schedule、start、complete、archive 等结构化事件。
- 任务决策日志记录“为什么这么做”：方案取舍、风险、接管说明、复盘。

当前不建议马上实现完整命令，原因是：

- 还没有足够多复杂任务证明需要新写入面。
- 如果默认给每个任务生成 Markdown，容易让用户误以为 Markdown 可以替代 JSON 真相源。
- 日志格式、归档位置、和 archive 的关系都需要再观察真实使用。

## 最小可行设计

如果后续排期实现，建议从很小的版本开始：

```text
.ai-board/tasks/T-0046.md
```

建议命令：

```bash
ai-board note T-0046 "记录一条决策或复盘"
ai-board note T-0046 --file notes.md
```

建议约束：

- 只允许给已存在任务写 note。
- note 文件是补充上下文，不参与任务状态计算。
- `archive` 不移动 note 文件，避免路径变化造成链接失效。
- `doctor` 只做轻提醒，例如 note 目录损坏或任务不存在，不做强校验。

## 建议后续排期

短期：

- 在 README 或 guide 里补一段“scope 门禁可以按需自建，不是默认能力”。
- 暂不新增依赖，保持默认安装简单。

中期：

- 新增可选 hook 示例，用现有 `ai-board locks/status` 和 git diff 做 warning。
- 观察多 agent 真实协作后，再决定是否需要 `ai-board note`。

长期：

- 如果复杂任务复盘频繁出现，再实现 `ai-board note`。
- 如果团队项目开始要求提交前强约束，再考虑提供可复制的 pre-commit 配置模板。

## 本次评估结果

- pre-commit scope 检查：适合作为可选模板，不适合默认启用。
- `ai-board note` / `.ai-board/tasks/T-XXXX.md`：方向成立，但先不实现，等真实复杂任务积累后再排期。
- 路线结论：不引入重依赖，不默认强制门禁，继续优先保持轻量和可解释。
