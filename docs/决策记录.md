## 记录

## 2026-05-13 使用 JSON 作为 v1 唯一真相源

- 背景：项目需要给 AI 和人一个稳定可操作的看板源，避免直接手写 Markdown 导致状态漂移。
- 选择：v1 使用 `.ai-board/board.json` 作为唯一写入源。
- 不选择：暂不使用 SQLite 作为默认存储。
- 原因：JSON 更轻，Git diff 友好，用户能手工修复，适合开源项目早期验证。
- 影响：后续如果出现并发写入、复杂查询、事件流审计需求，再评估 SQLite 后端。

## 2026-05-13 Markdown 只作为生成视图

- 背景：计划看板需要给人和 AI 阅读，但直接修改 Markdown 容易破坏结构。
- 选择：`docs/计划看板.md` 和 `docs/归档计划看板.md` 由 CLI 从 JSON 渲染。
- 不选择：不把 Markdown 当作状态写入源。
- 原因：保持单一真相源，减少多 agent 并行时的冲突。
- 影响：用户若手改生成的 Markdown，下次 `render` 会覆盖这些改动。

## 2026-05-13 v1 保持无第三方运行时依赖

- 背景：项目准备开源，初版应该容易试用和审查。
- 选择：CLI 使用 Python 标准库实现。
- 不选择：暂不引入 Typer、Rich、Textual、SQLite ORM 等依赖。
- 原因：降低安装门槛，减少维护复杂度。
- 影响：CLI 输出保持朴素；后续如果体验不足，再按需引入依赖。

## 2026-05-13 采用 skill + CLI 的分发形态

- 背景：用户希望项目像 `agent-browser` 一样，让用户安装 skill 后，AI 能通过 skill 学会调用终端 CLI。
- 选择：后续优先实现“轻量 skill 作为 AI 使用说明书 + 可直接运行的 `ai-board` CLI”。
- 不选择：不把所有命令说明长期硬编码在 skill 里。
- 原因：CLI 和 skill 分离后，AI 有稳定入口，人类也能在终端直接操作；同时可以减少 skill 内容过期。
- 影响：`T-0004` 作为 P0 排到下一批最前面，优先于普通开源材料补齐。

## 2026-05-13 安装和使用入口改为 AI 原生提示词

- 背景：`ai-board` 的主要使用者是 AI agent，不应只提供给人手动复制的安装命令。
- 选择：README、skill stub 和 CLI 内置 guide 都提供可直接交给 AI 的安装与项目接手提示词。
- 不选择：不把人工命令作为唯一主入口；不默认把 CLI 安装进当前项目虚拟环境。
- 原因：用户只需要把 GitHub 地址或提示词交给 AI，AI 应能自检、安装用户级 CLI、读取版本匹配 guide，并按看板流程工作。
- 影响：发布文档的第一入口变成“AI 帮你安装和使用”；人工命令保留为备用路径。

## 2026-05-14 skill 触发默认进入 onboarding

- 背景：实测发现 AI 安装并运行 `init` 后容易停在空看板，让用户再说明下一步，首次接手体验没有闭环。
- 选择：新增 `ai-board onboard --init-if-missing` 作为 AI 原生接手入口；当用户只触发 `/ai-board` 或只说“用 ai-board 接手”时，skill 和 CLI guide 要引导 AI 自动运行 onboarding。
- 不选择：不要求用户复制一大段项目接手提示词；不让 `init` 承担完整项目状态判断。
- 原因：用户安装 skill 后，AI 应能自己判断空项目、轻量新项目或已有项目，并提出“先规划 / 先补文档 / 继续执行”的下一步问题。
- 影响：`init` 仍是底层初始化命令；`onboard` 成为首次接手和安装后自检的主入口。

## 2026-05-14 暂缓 SQLite，优先事件日志作为存储增强

- 背景：当前 `board.json` 已能支撑轻量本地看板，但后续可能需要更好的审计、恢复和历史追踪能力。
- 选择：继续让 `.ai-board/board.json` 作为默认唯一真相源；后续存储增强优先考虑可选 `.ai-board/events.jsonl` 事件日志。
- 不选择：当前不把 SQLite 作为默认后端，也不马上引入多后端抽象。
- 原因：JSON 仍然更轻、更适合 Git diff 和人工修复；事件日志能补足历史追踪，而且不破坏现有快照模型；SQLite 的 schema、迁移、导入导出和调试成本暂时偏高。
- 影响：后续如果需要 `history`、审计或恢复，先围绕 JSONL 事件日志排期；只有在任务量、复杂查询、跨项目聚合或高频并发写入明显增长后，再重新评估 SQLite。

## 2026-05-14 使用 agent 身份池区分并发会话

- 背景：多个 Codex 或 Claude 会话同时工作时，单纯写 `owner_agent: codex` 无法区分“谁在做哪件事”，也不方便释放和复用负责人身份。
- 选择：在 `board.json` 中维护 `agents` 身份池；AI 会话先用 `agents claim --kind codex` 获取 `codex-00`、`codex-01` 等身份，再用该身份 start 任务。
- 不选择：不只依赖用户手写不同的 `--agent` 字符串；也不把身份机制替代 scope lock。
- 原因：身份池解决“谁是谁”，scope lock 解决“是否撞文件”，两者职责不同；身份加 lease 后，崩溃会话也能过期复用。
- 影响：看板负责人会显示更具体的身份；`archive` 会自动释放任务负责人身份；旧的 `--agent codex` 仍可兼容，但推荐使用 claim 出来的身份。
